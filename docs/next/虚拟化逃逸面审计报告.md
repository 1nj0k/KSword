# 虚拟化逃逸面审计报告

日期：2026-09-20
靶机：`KSword-HVM-Target`（Hyper-V Gen2，Windows 11 build 22621，testsigning on，单块 80 GB 合成 SCSI 盘）
被审对象：`KswordARKDriver/src/features/hvm/`（93 个文件）与其 R3 控制面

---

## 0. 这份报告回答什么，不回答什么

回答：**有没有一条路径，让本该被我们约束的一方拿到我们（VMX root）的权限。**

不回答：
- 我们的 hypervisor 能不能被它**下面**的东西（固件、另一个 L0、SMM）攻破；
- Windows 内核自身的漏洞；
- 没有实际编写利用代码。本报告的结论全部来自代码与实机读数，**没有做过利用验证**，
  所以"可达"是基于代码路径的判断，不是打通过的证明。

覆盖范围是**部分的**，具体缺口列在第 5 节。把"没审到"当成"没问题"是这份报告
最容易被误读的地方。

## 1. 实机验证：DDMA 读通路（前置条件）

篡改检测的全部结论都建立在"DDMA 读得对"之上——它若读错，`CPU 视图被重定向`
就是一台误报机器。所以先验这一条。

| 步骤 | 读数 |
|---|---|
| 暂存扇区取法 | 在 guest 建 1 MiB 已知图案文件，`fsutil file queryextents` 取 LCN，按分区偏移换算 LBA = **18880856** |
| **LBA 换算校验** | 按该 LBA 直接读裸盘，32 字节与写入图案**逐字节一致** —— 算错就会覆盖别人的扇区，这一步必须先过 |
| 传输探测 | `readyDisks=1`，`flags=0xc`（NAME_PRESENT + **SCSI_DMA_READY**）。ATA 为 `0xC0000010`，合成 SCSI 不支持，符合预期 |
| 自检 | 12 项全 PASS，含全部拒绝路径（缺 LBA / 缺确认 / LBA 0 非哨兵 / 跨页 / 未知 flag / 写缺 FORCE） |
| 往返比对 A | `pa=0x207E23000`（ntdll PE 头）：标准通道与 DDMA **64 字节逐字节一致**，五个阶段状态全 `0x0`（含 restore） |
| 往返比对 B | `pa=0x12CCA5000`（kernel32 PE 头）：同样一致 |
| **区分度反证** | 页内偏移 `0x100` 处两个模块内容**确实不同**（SizeOfCode `0x131000` vs `0x81000`），DDMA 精确跟随 —— 排除"回放同一份缓冲" |
| **还原反证** | 多次 DDMA 之后，1 MiB 暂存文件**损坏字节数 = 0** |

**结论：DDMA 读通路成立。** 注意两条边界：

- 这台是 Hyper-V 子分区，**证明不了 SLAT 绕过**（Gen2 只有合成 SCSI，且我们是被
  Hyper-V 虚拟化的一方）。这里证明的是**传输与备份/还原机制正确**。
- 写方向未验证。

## 2. 已核实为关闭的逃逸路径

这些是"本来可能是逃逸、实际不是"的，逐条给出代码位置。

### 2.1 非特权进程 → 内核 / hypervisor 控制面：关闭

`framework/device_control.c:56` 的控制设备 SDDL 现为
`D:P(A;;GA;;;SY)(A;;GRGWGX;;;BA)` —— SYSTEM 全权、Administrators 读写执行、
**其余任何人开不了设备**。

仓库里仍有 **102 个** `FILE_ANY_ACCESS` 声明（对比：`FILE_WRITE_ACCESS` 116、
`FILE_READ_ACCESS` 23）。`FILE_ANY_ACCESS` 让 I/O 管理器**完全不做访问检查**，
因此一个只读句柄可以下发任何这样声明的 IOCTL。但经核实，**HVM 控制面不在其中**：
`CONTROL_HVM` / `EPT_RULE` / `EVENTS` / `MEMORY` / `VIEW` / `MSR_POLICY` /
`CR_POLICY` / `DOMAIN` / `PROCESS` / `INJECT` / `NESTED_PROBE` / `NESTED_PAGE`
全部是 `FILE_WRITE_ACCESS`，只有 `QUERY_HVM` 是 `FILE_ANY_ACCESS`（查询类）。

遗留的是**纵深防御缺口**而非逃逸：管理员持只读句柄仍可下发那 102 个中的破坏性
IOCTL。源文件注释自己也记着这一条仍未收口。

### 2.2 vmcs01 的 HOST_* 字段被污染：关闭

`hvm_vmcs.c:1272-1296` 的 HOST 字段全部取自宿主 CPU 状态与驱动自算值。
`HOST_CR3` 特别地取 `KswordARKHvmCaptureSystemDirectoryBase()`（System 进程目录
基址）而**不是** `__readcr3()` —— 后者会拿到发起 IOCTL 的用户态进程页表，进程退出
后页被释放，下一次 VM 退出翻译不出 HOST_RIP，#PF → #DF → 三重故障、无蓝屏无转储。
代码里有一整段注释说明这件事，判断是对的。

### 2.3 vmcs02 的 HOST_* 来自 L1：关闭

这是嵌套 VMM 最直接的一条逃逸——若把 vmcs12 的 `HOST_RIP` 抄进 vmcs02，L2 一退出
就跳到 L1 指定的地址、并且在 VMX root 下执行。

`hvm_nested_l2.c:542-570` 的实现是：**在 vmcs01 还加载着时**把 host 字段读出来暂存，
`vmptrld` 到 vmcs02 之后再写回去。注释是 "Host state is always ours, never L1's"，
代码与注释一致。

### 2.4 exit MSR-LOAD 区被抄进 vmcs02：关闭（且是刻意的）

`hvm_nested_l2.c:845` 明确把 VM-exit MSR-LOAD（`0x2008`）排除在拷贝之外，理由写得
很准：该区是 VM 退出**之后加载宿主 MSR** 用的，而宿主是我们、不是 L1；抄过去会让
处理器在每一次 L2 退出时把 L1 的宿主 MSR 值加载进我们的 root 上下文。

对比之下 entry MSR-load（`0x200A`）与 exit MSR-store（`0x2006`）被拷贝，理由也成立
（分别作用于 L2 和 L1 自己的页）。这三者的取舍是本文件里最精细的一处判断。

### 2.5 VMCS link pointer 传递：关闭

`hvm_nested_l2.c:876` 恒写 `~0ULL`，不传播 L1 写的值。

## 3. 根因发现：VMM 不隔离自身内存

**这是本次审计唯一的实质性发现，其余所有线索都汇到这里。**

`hvm_ept_builder.c:588-598`（2 MiB 叶）与同文件的 1 GiB 叶路径，把**全部已安装
RAM** 发布为恒等映射叶，权限是：

```c
pdEntries[pdIndex] =
    (address & KSW_EPT_PHYSICAL_MASK) |
    KSW_EPT_READ | KSW_EPT_WRITE | KSW_EPT_EXECUTE |
    ...
```

全库 grep 未发现任何把 hypervisor 自身页从 EPT 摘除或降权的逻辑。因此：

> **来宾对每一个物理页都有读/写/执行权限，包括我们自己的 VMCS 区域、宿主栈、
> EPT 页表、MSR 位图与私有 IDT。**

直接后果（按可达性从高到低）：

1. 改 **EPT 页表**本身 → 任意改写映射 → 完全控制；
2. 改 **HOST_RIP 指向的代码页** → 在 VMX root 下执行任意代码；
3. 改 **宿主栈** → 同上；
4. 改 **MSR 位图** → 让本该退出的 MSR 访问直通。

### 3.1 下游：vmcs02 里未经校验的 L1 物理地址

`hvm_nested_l2.c` 把 L1 提供的若干物理地址**原样**写进 vmcs02，无任何范围校验：
MSR bitmap（`0x2004`）、entry MSR-load 区（`0x200A`）、**exit MSR-store 区
（`0x2006`，处理器往里写**）、虚拟 APIC 页（`0x2012`）。虚拟 APIC 的对齐校验存在但
是 `#if KSW_L2_ENFORCE_VIRTUAL_APIC_PAGE 0`（默认关闭，`hvm_nested_l2.c:514`）。

代码给出的理由是 "EPT01 is an identity map, so an L1 physical address is a host
physical address"。**这个理由在它自己的前提下成立**：既然 L1 本来就能直接写任何
物理页，在这里加范围校验不增加任何保护。

所以这不是一条独立缺陷，而是 3.0 的推论。**修 3.0 的时候必须连这里一起修**，
否则自身页保护会被 MSR 区这条路径直接绕过。

### 3.2 这算不算"漏洞"，取决于威胁模型

| 场景 | 我们相对谁更高特权 | 3.0 是否构成逃逸 |
|---|---|---|
| **A. thin VMM 跑在裸机，来宾 = 本机 Windows** | 不更高。驱动由管理员加载，来宾内核与我们同一信任域 | **否**。内核态攻击者本来就能读写物理内存 |
| **B. 我们在下、L1 是另一个 VMM（VMware/Hyper-V）** | 是。L1 应当被我们约束 | **是**。恶意 L1（或攻破了 L1 的 L2）可写我们的 root 结构 |
| **C. 我们托管 L2** | 是 | **是**，经由 L1 |

仓库文档对场景 B/C 已有**明确且反复的声明**，不是遗漏：

- `docs/next/ept-lease-contract.md:24`：「the prototype is not a security boundary
  against a malicious intermediate VMM」
- `docs/next/EPT切换后端设计.md:171`：「分离视图**不是安全边界**」
- `docs/next/hvm-memory-watch.md:59`：「这也是为什么它**不是安全边界**」
- `docs/next/arxiv/sections/design.tex:99`：同上

**未被文档覆盖的是机制本身**：上述声明都落在具体功能（租约、分离视图、watch）上，
而"EPT 恒等窗口 RWX 且不保护自身页"是它们共同的成因，文档里没有一处把这条单独
写出来。本报告的增量就在这里——把分散的"某功能不是边界"归到一个可验证的根上。

## 4. 建议

按投入产出排序。**三条都不是小改动，不建议在没有明确需求的情况下动。**

1. **先决定要不要做边界。** 若产品定位就是"内窥镜而非手术室"（现有文档与
   `ksword-thin-vmm-positioning` 的判断一致），那么正确的动作是**把 3.0 写进文档**，
   而不是改代码。误以为有边界比明知没有边界更危险。
2. **若要做**：把 hypervisor 自身的物理页从恒等窗口中降权（去写、去执行），
   并**同时**给 3.1 的四个 vmcs02 地址加范围校验。二者缺一则另一者无效。
   代价：自身页不再是连续大页，恒等窗口要按 4 KiB 拆分若干段，EPT 体积与
   TLB 压力都会上升；此外常驻期间自身页集合会变化（分配/释放），需要一套
   "改了自身页集合就重装 EPT 并广播失效"的机制。
3. **纵深防御**：把 102 个 `FILE_ANY_ACCESS` 里真正会改状态的那些改成
   `FILE_WRITE_ACCESS`。与逃逸无关，但能让管理员的只读句柄不再能下发破坏性操作。
   注意按 `ksword-new-op-bypasses-shared-checks` 的教训，改完要做变异测试。

- **场景 B/C 未实机构造**：需要在我们之下真的跑起一个 L1 并从 L1 侧发起攻击，

## 6. 一句话结论

**没有发现可由非特权方触发的逃逸路径**；经典的嵌套逃逸点（vmcs02 的 HOST 字段、
exit MSR-LOAD 区、VMCS link pointer）逐条核实均已正确关闭。

唯一实质发现是 **VMM 不隔离自身内存**：EPT 恒等窗口对全部 RAM 开 RWX 且不保护
自身页。这对当前主用场景（A）不构成特权提升，对嵌套场景（B/C）构成，而后者仓库
文档已反复声明不作为安全边界。本报告的增量是把这条声明的**机制根因**定位到具体
代码行，并指出 3.1 的 vmcs02 地址校验缺失是它的推论而非独立缺陷。
