Portable adversarial tests compile the same lease walker used by the driver and
exercise bit changes at each level, A/D modes, unreadable paths, root/path reuse,
and malformed requests.

\paragraph{Leaves larger than 4 KiB.}
A 2\,MiB or 1\,GiB EPT leaf terminates the walk one or two levels early, so a
short capture must still expire on the same drift a full path does, and the
levels it never read must stay outside verification. We extend the portable
suite to cover both leaf sizes: capture and validation on each, a full 64-bit
sweep of every captured entry requiring the ignored set to be exactly accessed at
any level plus dirty at the terminating leaf, A/D-disabled behavior, unreadable
leaves, and the guest offset folded into a large source frame. Two guest pages
inside one 2\,MiB leaf are shown to share an entry path and differ only in source
frame; both validate, which records that the lease proves path identity and never
guest-page identity. Rejections specific to a 1\,GiB leaf are included: address
bits inside its alignment, a non-writeback memory type, write without read, and a
permission intersection emptied by an ancestor.

Passing does not establish that a suite can detect anything, so we measure it.
Nine defects were injected one at a time into a copy of the walker: unchecked
reserved address bits under a large leaf, an unfolded guest offset, dirty treated
as metadata only at the last level, a large-page bit accepted at the PTE level,
validation that always walks four levels or that refuses short captures, an
accepted empty permission intersection, a 4\,KiB offset mask applied to every
leaf, and a capture that always reports four entries. The current suite kills all
nine. Run against the suite as it stood before these cases were added, three
survive, so the large-page cases are responsible for three of the nine and the
remaining six were already covered. The harness is scripted and rebuilds both
suite versions from the repository, so the count can be recomputed rather than
taken on assertion.

These tests validate comparator behavior against synthetic tables. They do not
replace hardware source-EPT mutation by a live intermediate VMM, adversarial
multicore, or actual hardware-failure tests.

\paragraph{Publishing an override at a larger granularity.}
\ks{} can publish an override as a 2\,MiB or 1\,GiB shadow leaf rather than a
4\,KiB one, allocating aligned contiguous replacement backing, initializing the
whole region from the original bytes so that publication changes nothing the
descendant can observe, and replacing individual pages afterwards. Admission is
gated on the granularity the intermediate VMM already uses: a leaf larger than
4\,KiB applies one permission set to every page beneath it, so it is admitted
only where EPT12's own leaf covers the whole region. Composing a 2\,MiB leaf over
512 separately mapped source pages would grant the descendant whatever the
sampled page allowed, including access the intermediate VMM revoked on one of the
other 511. A request that cannot be honoured at the granularity asked for is
refused rather than narrowed.

On the evaluated stack that gate never opens. Table~\ref{tab:large-leaf} reports
nine admission attempts against the running VMware/TinyCore instance. Seven
addresses captured a source translation, and every one of them terminated on a
4\,KiB EPT12 leaf; none reported 2\,MiB or 1\,GiB. All seven were refused with
the source-granularity status, one was refused on geometry, one address was not
mapped at all, and no override was published by any attempt.

That result measures the intermediate VMM rather than the mechanism: VMware backs
this descendant's guest-physical memory at 4\,KiB granularity, so a rule phrased
in terms of the source's granularity has nothing to admit.

\paragraph{Admitting by inspection instead.}
Coarse source granularity is sufficient for one leaf to stand for a region, but
it is not necessary. What a large leaf actually requires is that every source
entry under the region grant the same access and the same memory type, and that
can be established by reading them. \ks{} implements this as a second, explicitly
requested rule: it walks all 512 source entries of a 2\,MiB region and admits the
leaf only if they agree, treating accessed and dirty as per-page metadata rather
than disagreement. The rule is opt-in because it is paid for with a weaker lease
-- drift on the region's first page path is still detected at every composition,
while a change to one of the other entries is not, since re-reading 512 physical
entries inside a path that runs on the order of $10^{5}$ times per second is not
affordable. A caller that does not ask for it keeps the stronger lease and the
stricter rule.

Table~\ref{tab:large-leaf-scan} is that comparison on the live stack. The same
guest-physical address, the same driver and the same 4\,KiB source granularity
are refused under the coarse-source rule and admitted under the scanning rule,
which published a 2\,MiB shadow leaf over 2\,MiB-aligned contiguous replacement
backing; all 512 entries were read and reported the same access bits. Each
published region was removed, returning the active slot to zero, and the
descendant and its VMM ran throughout.

What this does not establish is a performance effect. We publish a large leaf and
remove it; we do not report an exit-rate or latency change from doing so, and the
page interventions measured elsewhere in this paper all target 4\,KiB pages. Nor
does the scanning rule make the lease equivalent: its weaker drift detection is a
property of the published region, not an implementation detail, which is why the
response reports which rule admitted it.

Sparse CPUID snapshots reduce the median from 2944.212 to 2915.062\,ns relative
to the matching nested full-snapshot reference, an observed 0.99\% change with
overlapping ranges. RTT does not improve. The sparse nested mode still costs
8.7594 times the off-mode CPUID time and 30.6914\% more loopback RTT. A small
telemetry optimization therefore does not resolve the major remaining cost.

Adding 512 VMREADs to ordinary residency increases median CPUID latency from
2905.918 to 6875.552\,ns. Dividing that difference by 512 estimates 7.753\,ns
per added read, including loop overhead. The 256-read result is consistent with
a similar marginal scale. Removing two reads cannot account for a
microsecond-scale end-to-end gap.

\paragraph{Where the added CPUID cost goes.}
A separate million-exit CPU~0 profile measures an average 382 TSC cycles for the
C dispatcher body, including 97 cycles for VMCS reads and 19 for telemetry. An
invariant-TSC calibration near 2.112\,GHz converts 382 cycles to 180.9\,ns.
Table~\ref{tab:attribution-budget} places that figure inside the measured cost of
one CPUID.

The profile is not free, and charging its cost correctly changes the answer. The
body takes eleven timestamps, and an empty back-to-back pair costs 25 cycles, so
roughly 65\,ns of the profiled 180.9\,ns is the instrument reading itself.
Subtracting one pair, which is the obvious correction, would credit the
dispatcher with most of that. We therefore report the dispatcher as a band whose
upper end is the raw profile and whose lower end removes all eleven readings.

That same 25-cycle pair is also the control the whole profile depends on. This
processor is itself a guest: if the outer hypervisor intercepted \code{RDTSC},
each of those eleven timestamps would be a VM exit of its own, and the
unexplained majority of the total would be the instrument rather than the
monitor. Two back-to-back reads answer that directly -- tens of cycles means the
readings stand, hundreds or thousands would invalidate every number here. The
measured 25 cycles is a native read.

The dispatcher accounts for 4.48\% to 7.00\% of the 2582.3\,ns that residency
adds to a CPUID, depending on which end of that band is taken. The residual is
93.00\% to 95.52\%, and we name what is inside it rather than leaving it
implicit: the hardware VM exit and entry, our own entry and exit assembly, and
the outer hypervisor's handling of an exit it must reflect to us. We do not split
those three. Every timestamp in this profile is taken inside our C dispatcher, so
none of them can observe anything on the far side of that boundary, and we have
no instrumentation inside the outer hypervisor. Reporting a finer split would
mean assigning time to code we did not measure.

Two independent measurements cross-check the one interior term that can be
checked. Adding 256 and 512 VMREADs to ordinary residency yields 7.957 and
7.753\,ns per added read, agreeing to 2.6\%. Dividing the profile's 45.9\,ns of
VMCS reads by the 512-read price implies 5.92 reads. The full snapshot path
issues exactly six VMREADs -- exit reason, exit qualification, guest RIP, guest
RSP, exit instruction length, and VM-instruction error -- and the profiled window
is dominated by exits that take it. The cycle count and the marginal-cost
experiment were collected separately and were not fitted to each other.

The same price explains why the sparse snapshot changes so little. It omits two
of the six reads for CPUID exits, predicting about 15.5\,ns; the observed
difference between full and sparse snapshots is 29.2\,ns with overlapping ranges,
so a two-read saving is at the resolution limit of this experiment rather than a
demonstrated effect.

The budget bounds what dispatcher-side optimization can achieve. Removing the
profiled body entirely -- not merely the telemetry or the VMCS reads -- would
move CPUID from 8.759 to 8.216 times the off-mode median, a 6.20\% reduction in
the on-mode cost, and that figure is generous because it credits the removal with
the instrument's own share. The measured 0.99\% gain from sparse snapshots sits
inside that ceiling, which is why we treat further telemetry trimming as
exhausted rather than promising. Reducing the residual is not a code change
available to us in this topology: it requires either fewer exits or a cheaper
exit path through the outer hypervisor, and the second is not ours to change.

RTT admits only a bound, not a budget. Residency adds 4020.7\,ns per loopback
round trip, which is 23.8 dispatcher bodies. That is an upper bound on the
dispatcher's contribution and is reached only if every one of those exits costs
a full dispatcher body and nothing else changes. RTT windows are dominated by
HLT, MSR, and hypercall exits rather than CPUID, so reducing CPUID work alone is
not a demonstrated networking optimization.

\paragraph{Exit and memory accounting.}
A historical nested benchmark window records 19,489,348 resident dispatches,
approximately 167,733 per second. VMREAD, HLT, VMWRITE, EPT violation, and CPUID
account for approximately 6.36, 5.64, 2.65, 2.55, and 0.82 million events.
The INVEPT-wrapper counter records 101,233 calls, about 874.4 per second, with
zero failures. Counter queries have different interval boundaries; their
denominators must not be mixed. These windows include startup and controller
work and are not isolated steady-state rates or global outer-Hyper-V counts.
An intercepted INVVPID instruction category is available, but an actual
hardware INVVPID total is not. Actual newly ORed A/D bits are zero in this
window, so it does not establish all A/D writeback semantics at runtime.

The historical optimized structures reserve a computed 3.25\,MiB of relevant
shadow tables, snapshots, and A/D ledger capacity per active CPU, or 13\,MiB
for four CPUs. This is a structure-capacity calculation, not a measured total
driver footprint. The increase trades memory and preparation cost for fewer
shadow-cache capacity failures.

\subsection{Reversible HTTP policy corruption}
\label{sec:application}
The application fixture uses an unmodified BusyBox HTTP server to serve a
4096-byte file-cache page containing a price policy. A separate fixed-schema
consumer validates the complete body and emits \code{quote-1250} for the valid
policy or \code{reject-corrupt-policy} for the zeroed replacement. HTTP status
200 alone is insufficient. A privileged guest helper uses mlock/pagemap to pin
and identify the page; this is explicit instrumentation.

The EPT intervention targets GPA \code{0x02479000}, with original Windows~1
backing \code{0xCCF89000} and replacement \code{0x204FD4000}. In three complete
trials, the observed decision sequence is valid quote, rejection, valid quote.
The strict HTTP/PFN join validates ninety responses, ten per stage per trial.
A second analysis tolerating unrelated serial-line interleaving validates
ninety-one policy observations; the extra observation is not counted by the
strict contiguous join. Table~\ref{tab:application-runs} retains the fourth,
incomplete attempt, whose bounded observer expires after five mapped samples.
Its successful removal and cleanup are retained. Extending the observation
window precedes the final complete trial.

Direct writing also works and may be the simpler choice when guest write
authority and restoration bytes are available. The fixture does not establish
production fault tolerance, a general JSON oracle, or agent-free page discovery.

\subsection{Intermediate Hyper-V: a negative compatibility result}
\label{sec:hyperv}
After upgrading Windows~1 to Pro, installing its Hyper-V role, and rebooting
outside measured intervals, a Generation~1 two-vCPU TinyCore fixture boots
through normal \code{/init}. The first two rebuilt ISO images fail in ISOLINUX;
the third succeeds. These setup failures are retained, with no claim that one
specific image field has been isolated as their cause.

In this configuration, Windows~1 is an \emph{inner Hyper-V root partition}.
Its CPUID.1 ECX is \code{0xFEFA3203}, with VMX bit~5 clear. The \ks{} capability
query returns \code{STATUS\_NOT\_SUPPORTED} (\code{0xC00000BB}), and both prepare
and resident-start requests are refused before a control IOCTL is submitted.
No resident processors or prepared resources are reported. A first CLI version
returned empty output with exit code~2; the corrected shared engine reports
the query stage and \code{controlSubmitted=false}. Neither is successful insertion.

Windows boot identity and child VM GUID remain stable around the first
admission attempt. The worker remains PID~2824 with the same creation time,
and child uptime advances from 203.659 to 203.784 seconds. The guest has its own
recorded boot ID and repeated normal-init heartbeats. This is positive evidence
for the Hyper-V/TinyCore fixture and negative evidence for \ks{} admission at
that insertion point.

Microsoft describes Hyper-V as a hypervisor below its root partition, whose
management stack creates child partitions~\cite{hyperv-architecture}. Exposing
nested extensions to a managed child~\cite{hyperv-nested} does not establish
VMX execution authority for another monitor in the inner root partition.
Installing the role therefore changes the topology; it does not simply replace
VMware with another process inside an otherwise unchanged Windows kernel.
We make no impossibility claim about all alternative architectures or future
builds. Descendant EPT control and live Hyper-V interposition remain unsupported
by these measurements.
